# 成熟 Agent 范式与约束调研

> 调研日期：2026-08-26  
> 范围：只引用 LangGraph、OpenAI Agents SDK、Microsoft AutoGen、CrewAI 的官方 GitHub 仓库或官方文档。  
> 目的：为本项目的 FOF / CTA 研究 Agent 确定下一阶段架构，而非引入一个通用聊天机器人。

## 结论先行

本项目应采用 **“有界状态机（workflow-first）+ 受控工具调用 + 人工确认关口 + 可审计记忆”**，而不是开放式多 Agent 自主协作，也不应把 ReAct 循环直接暴露给投资计算。

推荐的运行单元是一个可恢复的 `AgentRun`：每次用户请求先形成可展示的计划，再依次执行只读研究工具；遇到配置保存、导出、复核结论确认等状态变更时暂停，等待用户确认。所有净值、风险、归因、筛选、权重、组合回测和评分继续由确定性服务完成；LLM 只能理解意图、提出下一步、解释已经验证的结果。

这与 LangGraph 的持久状态图和中断模型最接近，也吸收 OpenAI Agents SDK 的 session、guardrail、tracing 设计。当前阶段不建议引入 LangGraph / CrewAI / AutoGen 依赖：现有 FastAPI、SQLAlchemy、任务审计和确定性量化服务已经能承载最小闭环，先把领域约束做完整比迁移框架更重要。

## 四个框架的范式比较

| 框架 | 主范式 | 工具调用与循环 | 记忆 | 人工审批 / 可观测性 | 对本项目的判断 |
| --- | --- | --- | --- | --- | --- |
| [LangGraph](https://github.com/langchain-ai/langgraph) | 持久化状态图；节点、边、条件分支和可恢复执行 | 工具可作为图节点；每个节点后都可根据状态路由、重试或停止 | 短期记忆属于线程状态并由 checkpoint 持久化；长期记忆跨线程、按 namespace 保存 | `interrupt()` 暂停并保存图状态，外部输入后恢复；LangSmith 提供轨迹、状态转换和运行指标 | 最适合作为架构参照：研究工作流本质上是有领域状态和审批点的图 |
| [OpenAI Agents SDK](https://github.com/openai/openai-agents-python) | 轻量 Agent 运行器；单 Agent、handoff 或 agent-as-tool | Agent 由 instructions、tools、guardrails、handoffs 组成；Runner 执行运行 | Sessions 自动管理跨轮对话历史 | 输入/输出 guardrails、内置 human-in-the-loop、run tracing | 最适合作为接口参照：工具 schema、运行轨迹、guardrail 与会话边界清晰 |
| [Microsoft AutoGen](https://github.com/microsoft/autogen) | 多 Agent 协作与 AgentChat | 多角色对话、MCP 工作台、工具迭代上限 | 对话和团队状态 | 可配置人工参与；支持流式运行 | 官方仓库已标为 **maintenance mode**，并建议新用户使用 Microsoft Agent Framework；不作为新依赖候选 |
| [CrewAI](https://github.com/crewAIInc/crewAI) | Crews（角色协作）+ Flows（事件驱动、状态与路由） | Crew 强调自治协作；Flow 强调精确流程控制，可混用 | 统一记忆支持保存、召回、来源和私有标记 | Flow 支持持久化与长运行恢复；任务和流程可加入 guardrails / 人工触发；提供事件与追踪能力 | “Flow 优先、Crew 只用于确有分工的子任务”值得借鉴；目前 FOF 研究不需要多角色自治 |

## 成熟 Agent 的通用约束

### 1. 状态机优先，不把“思考”当作业务状态

Agent 的可恢复状态应是业务对象，而不是模型的自由文本。建议一次运行至少包含：

```text
接收请求 → 形成计划 → 收集数据 → 确定性计算 → 校验结果
                                      ↓
                            需要用户决定 / 审批？
                                      ↓
                         暂停并展示选项 → 恢复执行
                                      ↓
                                   输出研究结论
```

每一阶段只允许有限状态：`planned`、`running`、`waiting_for_user`、`validated`、`completed`、`failed`、`cancelled`。这样前端能展示“正在做什么、已调用哪些工具、等待什么”，也能在服务重启后恢复或明确失败。

### 2. 工具是带权限和契约的领域能力

每个工具必须有：输入 schema、输出 schema、最大运行时间、读写等级、可用前置条件、审计摘要和失败码。LLM 只能从当前阶段允许的工具白名单中选择，不能直接访问数据库或调用任意 Python 函数。

建议的最小白名单：

| 工具 | 权限 | 确定性 | 使用条件 |
| --- | --- | --- | --- |
| `search_products` | 读 | 是 | 仅已确认、净值已复核的产品库范围 |
| `screen_products` | 读 / 计算 | 是 | 约束单 schema 校验通过 |
| `analyze_nav_risk` | 读 / 计算 | 是 | 选定产品存在足够净值数据 |
| `analyze_attribution` | 读 / 计算 | 是 | 因子覆盖与样本量满足门槛 |
| `optimize_portfolio` | 读 / 计算 | 是 | 产品数、权重、收益/风险约束通过校验 |
| `backtest_portfolio` | 读 / 计算 | 是 | 共同样本区间与权重和已校验 |
| `save_draft` | 写 | 是 | 必须在用户确认后调用 |
| `generate_explanation` | 读 / 解释 | 否（LLM） | 只能引用已验证工具输出 |

### 3. 记忆按用途分层，不能把聊天历史当作长期偏好

| 层级 | 内容 | 生命周期 | 写入方式 | 本项目规则 |
| --- | --- | --- | --- | --- |
| 运行状态 | 当前计划、工具结果、审批等待项 | 单次 `AgentRun` | 系统自动 | 必须可恢复、可审计 |
| 会话记忆 | 当前对话、当前选择产品、未完成追问 | `session_id` | 系统自动 | 限长度并可清空 |
| 用户偏好 | 明确确认的风险预算、策略偏好、语言偏好 | 跨会话 | 用户确认后写入 | 每条带来源、时间和可撤销标记 |
| 研究资产 | 已保存草案、已审核配置、历史反馈 | 长期 | 明确保存动作 | 绑定净值快照和计算版本 |
| 模型经验 | 可复用的成功/失败案例 | 长期 | 离线评估后写入 | 不直接改动投资规则或用户偏好 |

不应自动记忆：一次性的临时要求、模型猜测的风险偏好、未经复核的产品结论、任何凭证或敏感数据。长期记忆检索必须按用户 / 组织命名空间隔离，并向用户显示“本轮用了哪些偏好”。

### 4. 人工审批应放在风险边界，而不是每一步

建议分三级：

| 级别 | 行为 | 是否需要确认 |
| --- | --- | --- |
| 只读研究 | 查询、风险/归因/筛选/回测、生成解释 | 否 |
| 研究状态写入 | 保存配置草案、保存偏好、标记待复核 | 是，展示变更摘要 |
| 高影响动作 | 发布正式配置、导出给外部、覆盖既有版本、触发外部任务 | 强制确认，可拒绝或编辑 |

审批页面应展示确定性结果、数据截至日期、约束满足情况和即将写入的对象；不能要求用户确认模型的内部推理。

### 5. 可观测性是产品功能

每次 AgentRun 至少记录并回传：计划步骤、实际调用的工具、工具输入摘要（不含敏感字段）、耗时、候选数变化、数据快照、校验结果、LLM 是否参与、LLM 仅可见的证据 ID、最终结果和失败原因。前端展示简洁的“执行过程”；完整审计进入详情或后台。

需要设置运行预算：最大工具步数、单工具超时、总运行超时、最大候选数、最大上下文长度、最大 LLM 调用次数。超过预算时安全停止，返回已完成部分和下一步建议，不能静默循环。

## 推荐的下一版：配置 Agent 最小闭环

### 第一层：补齐当前领域模型（优先）

1. `AgentRun` 增加显式状态、计划步骤、审批请求、预算和失败码。
2. 将所有 FOF 约束固定成 versioned schema：最低年化、最高波动、最大回撤、最多产品数、单产品上限、策略偏好、数据最短周期。
3. 每个约束同时记录：原始文本、结构化值、来源（本轮输入 / 已确认偏好）、强度（硬约束 / 偏好）和置信度；含糊表达如“最好不超过五只”解析为偏好，无法满足时必须回问或明确放宽，不能静默忽略。
4. 在 `optimize_portfolio` 前后双重校验产品数、权重和、单产品上限与全部风险约束；违规结果不能发送给 LLM。

### 第二层：引入一次可控的 Agent 循环

每轮最多执行 5 步：

1. `plan`：LLM 将问题映射为固定任务类型与约束单；本地 schema 校验。
2. `retrieve`：调用许可的产品检索或研究数据工具。
3. `compute`：调用确定性筛选、优化、回测或归因工具。
4. `validate`：本地检查数据覆盖、约束满足、异常权重和结果一致性。
5. `respond`：若缺少关键条件则提出一个最小追问；否则 LLM 只基于证据生成结论。

循环只允许从 `validate` 回到 `retrieve` 或 `compute` 一次，用于修复“共同区间不足、候选不足、约束无可行解”等已定义场景。禁止 LLM 无限自主重试。

### 第三层：保存草案与确定性评分

新增两类对象并严格分离：

- **研究草案**：Agent 提出的候选、约束、理由、工具证据、组合历史表现；可保存、编辑、重新计算，但不可视为已执行配置。
- **已审核配置**：用户明确确认后的版本，绑定净值快照、计算版本、审批人、时间和审批说明。

评分由本地服务计算，至少包括：收益效率、回撤控制、分散度、约束满足度、数据可信度。LLM 可以解释分数差异，但不能给分或修改分数。

### 第四层：评估与持续改进

先建设离线评估集，不做模型自我学习：覆盖正常配置、约束冲突、候选不足、模糊偏好、产品数据缺失、审批拒绝、超时和中断恢复。验收指标应包含：

- 约束解析准确率；
- 违规组合拦截率（必须 100%）；
- 工具调用是否越权；
- 已完成运行的可复现率；
- 研究结论中的数值是否全部能回溯到工具证据；
- 用户对“下一步该做什么”的完成率。

## 明确不做的事

- 不采用无边界 ReAct：它不适合需要可解释、可审计、不可越过风控约束的 FOF 研究。
- 不为了“完整 Agent”拆成多个角色 Agent；产品筛选、组合优化和风险校验是确定性领域服务，不是独立人格。
- 不让 LLM 读取任意产品库、执行 SQL、计算指标、生成权重或直接保存配置。
- 不把所有聊天文本或工具输出都写入长期记忆。
- 不依赖 AutoGen 作为新项目底座；其官方仓库已处于维护模式。

## 实施顺序

1. 完成约束 schema、双重校验和无可行解反馈；这是正确性底座。
2. 将现有工具轨迹升级为有状态 `AgentRun` 和计划步骤。
3. 新增审批中断与恢复，先覆盖“保存草案”和“保存偏好”。
4. 增加草案库、快照绑定、确定性评分与离线评估。
5. 只有当出现真正需要并行、独立专业判断的非确定性任务时，再评估引入子 Agent 或外部编排框架。
